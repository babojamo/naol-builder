# Fashion Blessing semantics audit — 2026-10-13

The user selected documented flat PvE mechanics where the original brief requested percentages. Evidence: [official 1.5.5 blessing table](https://universe.flyff.com/index.php/news/muransawakeningexpansionv155) and [Flyffulator blessing data](https://github.com/Frostiae/Flyffulator/blob/main/data-src/Blessings.json). Reference data informed independently implemented rules; no reference implementation was copied.

1. **Existing calculation:** Fashion Blessings already flowed through `Gear.fashionBlessings`, `blessingAbilities`, and the canonical modifier collector with source type `fashion-blessing`. This architecture remains intact.
2. **Already correct:** STR, STA, DEX, INT, flat Attack, Defense, Magic Defense, HP, MP, FP and flat outgoing PvE Damage already had the intended flat semantics. Existing supported percentage consumers could read some untyped values, but operation metadata was absent and unreliable.
3. **Misclassification:** Every blessing was emitted without explicit `rate`. The nine percentage parameters below now emit authoritative rate metadata. Attack Speed required rate input to affect its formula. Legacy `castingspeed` and `pvedamagereduction` also used incorrect canonical parameter names; blessing-scoped aliases now resolve them correctly.
4. **Schema:** Added nullable boolean `rate` to authoritative rules. Runtime requires an exact active source/parameter/value match and a known, unambiguous operation. Unknown source may match either blessing source. Missing/conflicting operations are excluded. Saved blessing shape remains `{source, parameter, value}`.
5. **Flat parameters (12):** `str`, `sta`, `dex`, `int`, `attack`, `def`, `magicdefense`, `maxhp`, `maxmp`, `maxfp`, `pvedamage`, `pveincomingdamage`.
6. **Rate parameters (9):** `criticalchance`, `criticaldamage`, `speed`, `attackspeed`, `decreasedcastingtime`, `actionspeed`, `parry`, `meleeblock`, `rangedblock`. Production rule inventory: 92 Goddess + 112 Demon = 204; 21 parameters; unknown operation NONE.
7. **Attack Speed regression:** Demon +3% produces rate 3, flat 0, and increases both internal and displayed attack speed in the regression fixture. Source attribution retains the actual fashion item. Final speed still follows the existing formula and caps, rather than blindly adding three displayed points.
8. **PvE regression:** +10 PvE Damage enters the flat PvE attack stage, increases PvE damage and has no PvP effect. +10 PvE Damage Reduction subtracts a flat 10 from each normal/critical incoming hit before percentage reduction, with zero floor; with 20% reduction the net difference is 8. It does not become 10% reduction. The tank simulation retains its documented estimated encounter-model limitations.
9. **UI:** Fashion overview lists both configured lines, source and proper units. Source inspector displays rate units and item names. Character details distinguish flat PvE damage/reduction. Legacy parameter names remain editable. Data Health lists source counts, flat/rate parameter inventory and unknown-operation warnings. Head, suit, gloves, shoes and cloak stack; mask remains invalid; only two lines per piece calculate.
10. **Files:** `lib/fashion.ts`, `lib/model.ts`, `lib/repositories/flyff.ts`, `lib/supabase/database.types.ts`, `combat/character.ts`, `simulation/tank.ts`, `components/EquipmentEditor.tsx`, `components/CharacterDetails.tsx`, `components/DataHealth.tsx`, new `components/FashionBlessingSummary.tsx` and `components/FashionBlessingHealth.tsx`, `app/api/sync/route.ts`, rule seeder and loader scripts, test runner, three existing test fixtures, new `tests/fashion-semantics.test.ts` and `tests/fixtures/fashion-blessing-rules-1.5.5.json`, this report and migration below.

Both existing saved builds passed database schema validation afterward. No saved build payload changes or Edge Function changes were required.
